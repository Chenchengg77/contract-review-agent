# 错例库（failures）

> 记录开发过程中真实遇到的失败模式。每条五行：**现象 / 根因 / 归因层 / 修复 / 教训**。
> 归因层：L1 检索/解析层 · L2 生成层 · L3 判定层（沿用课程的分层归因法）。

---

## 1. 留空条款被误判为「缺失」

- **现象**：第一次抽取，家具合同的「第九条 付款方式及期限：」（内容留空）被 LLM 判成 `present=false`，导致付款条款漏报。
- **根因**：prompt 里没定义「留空也算存在」，LLM 默认「没内容 = 不存在」。
- **归因层**：L2 生成层（prompt 定义不清）。
- **修复**：prompt 增加「present=true 表示合同里出现了这类条款的标题，即使后面留空待填也照样算」。
- **教训**：对 LLM 的每个输出字段，都要在 prompt 里给到「边界情况的明确定义」，不能指望模型自己猜。

---

## 2. 「结算方式」没被识别为「付款条款」

- **现象**：承揽合同漏判 3 条（付款、终止、违约金），一致率 10/13。
- **根因**：用 playbook 的 `standard_text`（"甲方应在收到发票后…"）当识别依据太窄，模型认不出「结算方式」「解除」这些同义词。
- **归因层**：L2 生成层（条款描述不匹配）。
- **修复**：换成「识别关键词」提示（付款/结算/价款/租金…），一致率 10/13 → 13/13。
- **教训**：给 LLM 做「找条款」时，给关键词比给标准条款更有效；标准条款是用来「比对」，不是用来「识别」。

---

## 3. 表格型合同的条款被漏掉

- **现象**：木材订货、水路运输等老式合同，条款藏在表格里，解析后条款数 0。
- **根因**：最初用 `row.cells + id(cell._tc)` 去重，合并单元格（底层是 17×24 网格）被错误折叠，条款单元格丢失。
- **归因层**：L1 解析层。
- **修复**：改用 `table._cells` 遍历全部底层单元格 + **按文本去重**。
- **教训**：老式合同的结构不可控，解析层必须覆盖「表格藏条款」的情况；去重要按内容，不按对象 id。

---

## 4. 长合同撑爆上下文

- **现象**：建设工程施工合同、新能源并网协议等超长合同（数千段），全量塞进 prompt 有超限风险。
- **根因**：无上下文预算，短合同和长合同一视同仁。
- **归因层**：L2 生成层（上下文管理）。
- **修复**：`_format_contract` 加截断保护（条款标题优先保留、正文截短、总量封顶）。
- **教训**：成本与上下文要设预算（对应课程「成本意识」主线），先截断保底，再谈分块抽取优化。

---

## 6. 条款正文只取到标题，导致误判「缺失」

- **现象**：二手车买卖合同「第二条 车辆价款、过户手续费及支付时间、方式」明明有正文（价款、支付方式三选一、过户手续费承担），审查却判「付款条款：缺失（高）」；而 AI 对话对同一份合同能答出付款条款内容——两个模块结论矛盾。
- **根因**：判定流水线的 `_find_clause_text` 只取 `clause_no` 相同的段落（通常是标题行），没有把标题后续的正文段收进来。该函数隐含假设「标题与正文在同一段」——对「二、三、四塞一段」的老式合同成立，对「标题一段、正文在后」的新式合同不成立。
- **归因层**：L1 解析/取数层（**不是 RAG**，RAG 检索全文正常，所以对话能答对）。
- **修复**：两层——① 标题后收集正文段，直到「下一个主条款（第X条 / 一、）」才停，编号小节（1.1 / 1. / （一））继续收；② 同一条款号出现多次（目录 + 正文）时，取正文最长的那条。
- **教训**：① 「同一条款在哪一段」这类假设要显式验证，别默认文档结构统一；② 模块之间结论矛盾时，先对比两边的**输入**，问题往往在取数层而不是模型层；③ 修完要写脚本扫全量（31 份合同，「疑似只取到标题」6 → 1，剩 1 是文档本身空白），不能只测一个案例。

> 面试表述注意：**不要说"RAG 只检索了标题"**（错）。正确说法是「**审查判定**取条款正文的函数只取了标题行，RAG 本身正常」。
