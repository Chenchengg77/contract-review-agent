## 一、简历三行（三段式写法）

**① 做了什么 + 规模**
构建前后端分离的**合同智能审查平台**（FastAPI + LangGraph + DeepSeek）：解析 DOCX 抽取 13 类关键条款，做**合规/偏离/缺失/冲突**四态风险判定，高风险条款经人工确认后生成带原文定位的审查报告；另提供**基于合同的 RAG 问答**（带引用、能拒答）和**合同对比**（逐条差异）。

**② 用了什么关键手段 + 为什么**
LLM 结构化抽取 + **「原文可搜」校验**防幻觉；**LangGraph 编排 + interrupt 人工确认 + checkpoint 断点续跑**（高风险场景必须人机协同）；BM25 检索支撑合同问答与相似条款查询；**评估先于优化**，全部数字可复现。

**③ 结果 + 代价**
自建 **403 条**评估集、31 份合同：抽取准确率 **95.53%**（F1 92.57%）、verdict 准确率 **91.07%**、severity 准确率 **94.54%**、冲突判定在填充样本上 **100%**；单份合同审查约 **2 秒**、成本约 **1 分钱**。

> 每个数字都要能 3 秒内指出出处：`results/eval_v3.json` 哪一行。

## 二、面试八问（脱稿练）

| 问题 | 考察点 | 答案要点 |
|---|---|---|
| 为什么用 RAG/抽取，不微调？ | 技术选型 | 知识更新频繁（范本会变）、必须可溯源（引用原文）、微调改行为不改知识、无标注数据 |
| 你的条款怎么"切"的？ | 是否懂原理 | 解析出「条款号+标题」结构（第X条/一、/1.1），按类型关键词定位；表格里的条款也解析并去重 |
| 准确率多少？怎么测？ | 是否真评估过 | 抽取 95.53% / F1 92.57%；403 条 gold set，`evaluate.py` 一键复现 |
| 抽取不准怎么办？ | 排查能力 | 分层归因 L1解析/L2生成/L3判定，`failures.md` 有真实错例 |
| **AI 对话怎么做、怎么防瞎编？** | RAG 理解 | BM25 检索合同段落 → LLM 只基于原文回答 → 要求引用条款号 → 找不到就**拒答** |
| 幻觉怎么控制？ | 工程严谨 | 抽取：证据必须原文可搜；问答：无则拒答；报告：高风险人工确认 |
| 怎么防 Agent 死循环？ | 生产经验 | 流程是线性 DAG（无循环），这是针对高风险审查场景的**刻意设计** |
| 成本怎么优化？ | 工程能力 | 长合同截断、条款标题优先、规则层先行（零 LLM 成本）、temperature=0 |

## 三、说出自己系统的三个缺陷（必考）

1. **数据局限**：31 份中只有 2 份是「填充示例」，其余是空白示范文本，缺大量真实「合规/冲突」样本；
2. **判定层数字不够硬**：verdict 准确率 91.07%（修复"正文只取标题"的 bug 前是 85.36%），仍受 gold 规则标注与语义判定边界分歧影响，需人工精标才对得公平；
3. **检索仍有 4 条漏检**：30 条金标里，混合+rerank 后 Hit@3 80%，剩下 4 条都是空白范本的表格碎片，属数据问题；另外 LangGraph 的 checkpoint 还在内存里，服务重启会丢待确认任务，上生产要落库。

> 敢说缺陷，比只会吹"效果很好"可信十倍。每个缺陷后面跟一句「下一步怎么办」。

## 四、脱稿 5 分钟讲什么（框架）

1. **解决什么问题**：合同审查耗时、高风险条款漏检，2 小时 → 2 秒。

3. **两个关键取舍**：① 为什么人工确认（高风险不能全自动）；② 为什么评估先于优化。
4. **数据与数字**：403 条评估集 + 95.53% 的来源；冲突判定 100%。
5. **三个缺陷 + 下一步**。
6. **演示**：六个模块（审查/对话/对比/评估），点开就能用。
